**Task 1**
What is software?
Software is a set of programs and instructions that tell a computer or other device what to do. Unlike hardware, software is not a physical part of a computer. It includes things we use every day, such as operating systems, mobile apps, games, web browsers, and programs like Microsoft Word. Software allows users to perform different tasks and helps the hardware word correctly. It is created by writing code using programming languages such as Python, Java, or C++.

What does engineering add to that?
Engineering means designing and building something in a planned way, so software engineering means building, testing, fixing, and maintaining software. For example you can write a little python calculator and that would be software but if you want to build a big banking app used by millions of people, you would need to think about the security, testing, databases, bugs etc. That's where the engineering part comes in.

Success/Failure
Last year, for Team Project module we developed an airline ticket booking website. We had problems getting different parts of the system to work together properly, Better planning and more testing throughout development could have prevented some of these issues.



**Task 2**
Stage 1 - Kick off
Specification was weak.
There was only one meeting that lasted an hour.
The IT director only explained roughly what the system needed to do.
No requirements were written down.
The warehouse staff was not asked what they needed from the system.
The developer assumed he understood everything and started designing straight away.

Stage 2 - Development
Development was present, but it was poorly managed.
The three developers were each working on different parts of the system.
They did not communicate or work together enough.
There were no coding standards or code reviews.
They were all putting their code into the same shared folder.
This sometimes caused the to overwrite each others work.
The warehouse staff were still not involved, so the developers were building a system based on their own assumptions.

Stage 3 - A change of plan
Evolution was present, but weak.
A new requirement was added for a second warehouse.
The second warehouse used a different shelving and barcode system.
This was a big change that had not been planned for at the start.
The developer thought it would only add a few weeks.
Instead of changing the original design properly, they added the new requirements on top of what they already had.
This caused problems later when the system went live.

Stage 4 - Testing
Validation was present, but very weak.
The developers only tested the system for two days.
They mainly fixed crashes and problems that they found themselves.
There were no proper written test cases.
The warehouse staff were not allowed to test the system before it wen tlive.
This meant problems with how the system actually worked compared to work in the warehouse.

Stage 5 - Go live
Validation had failed and evolution was needed.
Warehouse staff finally got to use the system and immediately found problem.
The stock transfer screens did not match how stock transfers actually worked.
The second warehouses barcodes were not accepted.
When two people used the system at the same time, stock counts could become corrupted.
The system had to be taken out of use after only one week.
The developers then had to make more changes which added three months to the project.

Biggest Failure
I think the biggest failure for this project was the weak specification at the start.
The developers never properly found out what the warehouse staff needed.
They started building the system based on assumptions.
If the warehouse staff had been involved from the beginning, problems such as the incorrect stock transfer screen would have been found much earlier.
Having proper written requirements would also have made it clearer what the system was supposed to do.
The first mistake had a knock on effect on the rest of the project and caused many of the problems that appeared later on.
